# ワークスペースのメンバー管理と招待（承諾制）

## 目的
セキュリティレビュー（2026-11-04）で次の 3 点が見つかった。
- 研究室のメンバーが抜けてもアクセスを取り消せない（メンバーの削除・権限変更 API がない）。
- `POST /workspaces/{id}/members` の 404 / 201 でアカウントの有無が分かる。
- 本人の同意なしに他人を共有ワークスペースに入れられる。Phase 3 のライブラリ横断 RAG では、悪意ある PDF を入れたワークスペースに他人を追加すると、その人のチャットにプロンプトインジェクションを届けられる。

## 要件
- [x] R1: `POST /workspaces/{id}/members {email, role}` は、メンバーを直接追加せず**招待**を作る。アカウントがあってもなくても、無効化されていても、**同じ 202 と同じ形のボディ**を返す。アカウントがまだないメールへの招待は、後からその人がアカウントを作れば見える。すでに保留中の招待があれば role を上書きし、ここも 202 を返す。対象がすでにメンバーなら 409（owner はメンバー一覧を見られるので、存在確認の手段にはならない）。
- [x] R2: 招待された本人は `GET /invitations` で自分宛ての保留中の招待（ワークスペース名・role・招待者の表示名）を見られる。`POST /invitations/{id}/accept` でメンバーになり、`POST /invitations/{id}/decline` で辞退する。他人宛ての招待 ID は 404。期限（14 日）を過ぎた招待は一覧に出ず、承諾もできない。
- [x] R3: owner は `GET /workspaces/{id}/invitations` で保留中の招待を一覧でき、`DELETE /workspaces/{id}/invitations/{invitation_id}` で取り消せる。
- [x] R4: owner は `PATCH /workspaces/{id}/members/{user_id} {role}` で権限を変えられる。
- [x] R5: `DELETE /workspaces/{id}/members/{user_id}` で、owner は任意のメンバーを外せる。owner 以外のメンバーは自分だけ外せる（脱退）。外れた直後から、そのワークスペースのすべての API が 404 になる。
- [x] R6: 最後の owner を降格・削除しようとすると 409。personal ワークスペースのメンバー操作と招待は 400。
- [x] R7: ワークスペースの作成・招待・権限変更・メンバー削除・招待の承諾と辞退は、**Cookie セッションだけ**で行える。PAT では 403。
- [x] R8: 招待の作成は、1 ユーザーあたり 30 回/時のレートリミットをかける（`app/core/ratelimit.py` を再利用）。
- [x] R9: 設定画面に「ワークスペース」セクションを追加する。
  - 共有ワークスペースの作成。
  - 自分宛ての招待の承諾と辞退。
  - 所属する共有ワークスペースごとのメンバー一覧。owner には招待フォーム、権限の変更、メンバーの削除、保留中の招待の取り消しを出す。owner 以外には脱退ボタンを出す。
  - ja / en 両方の辞書を用意する。
- [x] R10: 招待を承諾・脱退した後、ヘッダーのワークスペース切り替えの一覧も更新される。

## スコープ外
- 招待メールの送信（SMTP がない。招待された本人がログインして設定画面で見る）
- ワークスペースの名前変更と削除、owner の移譲（owner を 2 人にしてから外せば代わりになる）
- ユーザーの無効化とパスワードリセット（レビューの別項目）
- 監査ログ

## 受け入れ基準
- backend の pytest が全件通る（既存のメンバー追加を使うテストは、招待して承諾する形に直す）。
- 新しく足すテスト（`tests/test_members.py`）で R1〜R8 を確認する。
  - 存在する / しないメールで、ステータスとボディが同じになる。
  - 他人の招待は承諾できない。
  - 期限切れの招待は承諾できない。
  - 外されたメンバーはそのワークスペースの論文に 404 になる。
  - 最後の owner は降格・削除できない。
  - PAT では 403 になる。
  - 招待のレートリミットに当たると 429 になる。
- `tests/test_migration.py` が通る（マイグレーション 0004 とモデルが一致している）。
- frontend の lint / typecheck / build が通る。
- Playwright で確認する：owner が招待 → 招待された側が設定画面で承諾 → ヘッダーに共有ワークスペースが出る → owner が viewer を editor に変更 → owner がメンバーを削除 → 削除された側から共有ワークスペースが消える。

## 決めたこと
- **招待はメールアドレスに紐付ける**（ユーザー ID ではない）。アカウントの有無を応答で分けないためと、アカウントを作る前に招待できるようにするため。比較は CITEXT（大文字小文字を区別しない）。
- **期限は 14 日の固定値**にする（設定項目は増やさない）。期限切れの行は消さず、読むときに除外する。
- 承諾したとき、すでにメンバーなら招待を消して 200 を返す（冪等）。
- owner による owner への昇格は許可する。owner 同士で外し合うこともできるが、最後の 1 人は守る。
- 招待の一覧は owner だけが見られる。editor と viewer はメンバー一覧だけを見られる（今と同じ）。
- `POST /workspaces` も session 限定にする。PAT のスコープ名は `papers` で、メンバーシップの管理まで含める意図はなかった。
- 実装中に追加で決めたこと
  - 招待の一覧（`GET /invitations`、`GET /workspaces/{id}/invitations`）も session 限定にした。
  - 同じメールへの再招待は、role・招待者・期限（今から 14 日）を上書きする（`ON CONFLICT DO UPDATE`）。同時に招待しても 500 にならない。
  - 承諾はメンバーの INSERT を `ON CONFLICT DO NOTHING` にした。既存メンバーの role は変えない。二重承諾でも 500 にならない。
  - レートリミットは owner と personal の検査の後にかける。owner でなければ 429 ではなく 404 になる。
  - 権限変更とメンバー削除では、メンバー行を `FOR UPDATE` でロックし、最後の owner の判定が競合しないようにした。
  - `test_tokens_api.py` のスコープ検査は、`POST /workspaces`（PAT では 403 になった）から `POST /papers/metadata-only` に置き換えた。
  - 権限の表示名は、ヘッダーの「（閲覧のみ）」に合わせて「閲覧のみ / 編集可 / オーナー」（en: view only / can edit / owner）にした。
